# UI 引擎子系统升级（提案）

> 状态：**已退役**。本文是 2026-11 的子系统升级提案，已被 [docs/engine](../README.md) 系列取代，保留作历史记录。
>
> 原状态：提案，未定稿。本文不改变 `docs/ARCHITECTURE.md` 已定的事实；进入实现前，先把这里标成【决定】的条目合入事实文档。
> 基线：`main@f090ea1`。实测 Python 365 条、TS 288 条测试全绿（`uv run pytest -q`、`pnpm --dir app/ui-engine exec vitest run`）。

## 0. 结论

`app/ui-engine/` 已经不是【把节点树画出来】的小库，而是整个产品的界面子系统。它同时承担五件事：

1. 与 Python 侧保持一条可验证的视图契约；
2. 组合多个插件交来的贡献；
3. 维护每个客户端连接的视图版本与订阅；
4. 承载事件路由、错误隔离和生命周期；
5. 将来还要承载 TS 插件与组件扩展。

因此升级目标不应是【再加一些组件】，而是把引擎收敛成 **UI runtime / subsystem**：层与层之间只有明确合同，新增界面能力不靠改引擎内部。现有方向是对的，缺口主要在合同闭合、页面写作模型、TS 插件宿主和可观察性。

## 2. 现状审计：真正缺什么

### 2.1 合同没有完全闭合

- `docs/design/ui-plugins.md` 定了 `replace` / `before` / `after` / `append` 四种挂接动作，组合器也支持。
- 但 Python 的 `Ui.contribute()` 没有 `op` 参数，服务端始终发 `op=append`。四种动作里只有一种能从插件侧真正使用。
- 这是接口缺口，不是文档缺口。应优先补齐，否则贡献模型只完成了 TS 单侧。

### 2.2 页面写作模型还没有定

- 当前页面树由插件每次重建，服务端再对整页做 diff；补丁能省传输和解析，但插件侧仍然整页构造。
- 静态骨架只能证明空数据下结构长这样，还不能证明同一个页面换一套数据后结构不变。
- 因此脏贡献重组、跨数据骨架检查、局部刷新都缺一个共同前提：**结构声明与数据绑定分开**。

### 2.3 TS 插件宿主不存在

- 现在所有节点都在 React 组件注册表里，新增组件类型必须改 `render/components.tsx`。
- 【写一个新插件，`app/ui-engine/` 一行都不用动】目前只对 Python 节点贡献成立，对 TS 半边不成立。
- 运行后插件的目录、清单、装载方式、信任模型都未定，不能先写加载器再补安全边界。

### 2.4 引擎仍含有产品/领域组件

- `capture/`、`search/`、媒体播放等实现直接住在 `app/ui-engine/src/`。
- 文档原则是【引擎里出现的名字是平台的名字】；现状更像引擎加部分插件实现的混合体。
- 在 TS 宿主出现前，这些组件暂时搬不干净；但应先登记归属，避免继续把领域组件塞进核心词表。

### 2.5 生命周期和可观察性不足

- Python `ui` 插件有 `ctx.effect` 清理，但 TS 侧没有同等粒度的卸载账本：组件、订阅、监听、贡献没有统一登记与逆序撤销。
- 没有 UI runtime 指标：组合耗时、补丁大小、丢弃贡献数、未知组件数、迟到 handler 数，只能从零散日志猜。
- `static_ui.py` 的哈希只覆盖导航 `pages`，不覆盖页面骨架；导航不变而结构变化时，旧骨架不会被判为过期。

### 2.6 文档之间已出现重叠和过期数字

- `ui-engine.md` 讲数据流与组件，`ui-plugins.md` 讲键与贡献，两者对窗口 / 页面 / 贡献的边界有重复描述。
- 测试数量等事实已落后于代码。文档应合并成一份 UI runtime 主文档加少量专题文档，减少改一处忘一处。

## 3. 目标与非目标

### 目标

- 定义 UI runtime 的稳定分层：合同层、组合层、渲染层、连接会话层、插件宿主层。
- 四种贡献动作从 Python 到 TS 全链路可用，并有跨语言测试。
- 页面模型能明确区分结构与数据，支撑静态骨架稳定性检查和局部更新。
- TS 插件可以注册组件、贡献视图、订阅事件、被卸载，并且不需要修改引擎源码。
- 失败隔离、卸载撤账、版本兜底、性能指标都有可执行验收。

### 非目标

- 不做通用前端框架、虚拟 DOM 替代品、SSR 或跨进程响应式框架。
- 不为了统一把 Python 领域逻辑搬到 TS；真相仍在 Python。
- 不在这一轮做深色主题、窄屏重排、多客户端路由或视觉改版。
- 不为尚未出现的第二个真实用例预造完整插件市场、权限系统或依赖图。

## 4. 目标架构

```text
Python 插件
  └─ omora.sdk.ui 节点 / 页面 / 事件载荷
       └─ ui 系统插件：页面登记、handler、快照 / 补丁、topic 声明
            └─ net：帧、订阅、推送
                 │  一条消息协议
                 ▼
TS UI runtime
  ├─ Session        每连接一份：连接状态、当前页、version、订阅
  ├─ SnapshotStore  全量 / 补丁 / 兜底重拉
  ├─ Composer       键 + 贡献 → 一棵树 + key index
  ├─ PageModel      骨架 / 数据段 / 局部更新边界
  ├─ Renderer       节点 → React；memo + 错误边界
  ├─ PluginHost     TS 半边：注册、贡献、服务、卸载
  └─ Diagnostics    指标、日志、调试索引
       └─ Shell / Window / ComponentKit
```

分层规则：

| 层         | 可以做                           | 不可以做                     |
| ---------- | -------------------------------- | ---------------------------- |
| Contract   | 定义数据形状、版本、错误码       | 依赖 React、连接实现或业务词 |
| Session    | 管理连接内快照、版本、订阅、重放 | 解释节点内容或业务状态       |
| Composer   | 纯函数组合、键索引、死键诊断     | 请求数据、判断业务对错       |
| PageModel  | 组织骨架与数据段                 | 持有领域真相                 |
| Renderer   | 节点映射组件、错误隔离、memo     | 改业务状态、发领域请求       |
| PluginHost | 装载 / 卸载插件、登记能力        | 让插件绕过合同直接改引擎内部 |
| Shell      | 窗口区域与导航                   | 猜页面内容                   |

边界判据不变：**引擎只做执行，不做判断。**

## 5. 需要拍板的三个核心决定

### D1. 页面写作模型

建议采用 **B-lite：声明式骨架 + 数据段 + 显式刷新边界**，不引入完整响应式框架。

- 页面由 `skeleton()` 声明结构，节点上带稳定键；
- 数据通过 `data(section)` / `refresh(section)` 填入或刷新；
- 结构变化才换骨架，数据变化只更新对应段；
- Python 仍产出完整节点数据，TS 不猜业务。

验收：

- 两套差异很大的 fixture 生成同一骨架；
- 同骨架下只改数据，产出的补丁不触碰结构节点；
- 现有 `PageHandle.set()` / `refresh()` 有迁移路径，不要求一次改完四个页面插件。

备选：

- A. 保持每次整页树：最省设计成本，但接受整页构造与骨架不稳定；
- C. 由 TS 组件自己取数据：会把真相与业务判断拉进 TS，和现有边界冲突，不建议。

### D2. TS 插件宿主的阶段

建议分两阶段：

1. **编译期系统 UI 插件**：随包构建，只通过 `PluginHost` 注册；先证明卸载、组件命名空间、错误隔离。
2. **运行后 UI 插件**：等目录、清单、信任模型和分发格式定了再开。

第一阶段的宿主接口应包含：

- `activate(ctx)` / `deactivate()`；
- `ctx.registerComponent(namespacedType, component)`；
- `ctx.contribute(target, tree, op, order)`；
- `ctx.on(topic, handler)`；
- `ctx.log` / `ctx.diagnostics`；
- 所有登记物自动进入卸载账本。

### D3. 四种贡献动作的同一语义

- Python API 增加 `op` 参数，服务端不再硬编码 `append`。
- 四种动作共用同一套全序、幂等、成环与死键规则。
- 同一贡献的身份应是 `(owner, target, op, seq)`；替换到达时更新而不是追加。
- 跨语言 fixture 至少覆盖：append、before、after、replace、成环拒绝、死键、重复到达。

## 6. 运行时合同（方向，不是最终代码）

建议拆出以下概念，具体名字实现时再定：

```ts
interface UiSession {
  open(): void;
  close(): void;
  render(page: string | null): Promise<Snapshot>;
  dispatch(handler: string, payload: JsonObject): Promise<void>;
  subscribe(topics: string[]): Promise<void>;
}
```

```ts
interface ViewRuntime {
  compose(snapshot: Snapshot): ComposeResult;
  render(tree: Node): ReactNode;
  index(): ReadonlyMap<string, Node>;
  diagnostics(): ViewDiagnostics;
}
```

```ts
interface PluginHost {
  activate(plugin: UiPlugin): Promise<void>;
  deactivate(owner: string): Promise<void>;
  unloadAll(): Promise<void>;
  inventory(): PluginInventoryEntry[];
}
```

要求：

- `UiSession` 不依赖具体 React 组件；
- `ViewRuntime` 可以脱离连接层单测；
- `PluginHost` 不把 React 实例泄漏成跨插件全局；
- 所有异步操作在卸载后返回时不得再写状态。

## 7. 生命周期、失败与安全

### 生命周期

1. 连接打开 → 上报设备 → 重建订阅 → 请求当前页；
2. 快照到达 → 校验形状 → 应用全量或补丁 → 组合 → 渲染；
3. 事件 → 发往 Python → 新快照 / 补丁推回；
4. 插件卸载 → 撤销贡献、订阅、监听、组件登记；
5. 连接关闭 → 清空本连接订阅和运行期状态，不保留跨连接脏引用。

### 失败

- 未知组件：本节点降级占位，兄弟节点继续渲染。
- 组合失败：单份贡献降级，壳和其余贡献继续。
- 补丁版本不匹配：请求全量，不猜测。
- 迟到 handler：只允许一次宽限，并记指标。
- 插件 `activate` 失败：整个插件回滚，不影响其他插件。
- 卸载失败：记录失败项，继续撤其余项，最后汇总报错。

### 安全

- TS 运行后插件在本机渲染进程中运行，默认等同于完整权限；没有沙箱前不宣称安全插件。
- 在信任模型定下来之前，只允许编译期系统插件进入宿主。
- 生态插件加载必须同时满足：清单可验、入口可定位、React 单例、CSS 隔离、卸载测试、版本握手。

## 8. 测试与验收

### 必须钉住的性质

- 组合幂等：同一贡献重复到达不重复挂。
- 顺序无关：输入顺序变化不改变结果。
- 全量兜底：任意补丁失败后仍能回到可用视图。
- 增量等价：增量应用结果等于同一输入直接全量组合。
- 卸载零残留：贡献、监听、订阅、组件全部撤销。
- 失败隔离：一个坏节点 / 坏贡献 / 坏插件只影响自己。
- 骨架稳定：同一页面在两套 fixture 下结构一致。
- 跨语言：Python 序列化与 TS 解析对同一 fixture 的结论一致。

### 分阶段验收

| 阶段          | 内容                                    | 退出条件                           |
| ------------- | --------------------------------------- | ---------------------------------- |
| E0 基线       | 审计、测试清点、文档合并                | 现有测试全绿；状态表与代码一致     |
| E1 合同闭合   | Python 四动作、贡献身份、跨语言 fixture | 四种动作端到端可测；不靠手写字符串 |
| E2 页面模型   | 骨架 / 数据段、局部刷新、骨架 fixture   | 两套 fixture 同骨架；增量不碰结构  |
| E3 TS 宿主    | 编译期插件、组件命名空间、卸载账本      | 示例插件的界面能力不改引擎源码     |
| E4 组件归属   | capture / search 等逐步迁出核心         | 引擎词表里不再有产品名             |
| E5 运行后加载 | 清单、加载、信任、隔离门槛              | 有完整卸载与失败回滚测试           |
| E6 观察性     | runtime 指标、调试面板、性能基线        | 组合 / 补丁 / 渲染成本可测         |

## 9. 风险与停止条件

- **页面模型变成自研框架**：一旦需要发明调度器、依赖追踪、生命周期 DSL，就停下来重新评估；先用 B-lite 的最小形态。
- **TS 宿主变成权限黑洞**：没有信任模型就不开放运行后插件。
- **为了统一把业务搬进 TS**：违反 TS 不持有真相，立即退回。
- **组件数量膨胀**：只按真实页面缺口加组件，不按清单刷数量。
- **文档先行但代码不跟**：每一阶段必须同时合入实现、测试和事实文档，不能只写设计。

## 10. 现在就能做的最小批次

1. 把 `ui-engine.md` 与 `ui-plugins.md` 的重叠部分合并成一份 UI runtime 主文档，并修正过期测试数字。
2. 给 `Ui.contribute()` 增加 `op`，打通 Python 到 TS 的四种动作，加跨语言 fixture。
3. 为页面模型写一份 1 页 ADR：只回答结构与数据是否分开，不同时设计完整 API。
4. 给 TS 侧补一个卸载账本最小实现，用编译期示例插件验证。
5. 把静态骨架哈希从导航哈希升级为导航加结构哈希，并加两套 fixture 的稳定性检查。
