# 版本设计

只有一个版本号，属于软件。系统插件不单独定版本。

## 1. 一条规则

> 系统插件的版本号 = 软件版本号。

它们跟软件一起构建、一起发布、一起升级，所以不存在"软件 0.3 配插件 0.2"这种状态。
兼容问题不靠 semver 解决，靠**不存在两个版本**来消除。

这条只约束**系统内部**的插件。系统外的不在这个范围里，见第 5 节。

## 2. package 元数据照填，但不参与解析

系统插件仍然是一个 package（Python / TS / 别的），元数据里该有的版本字段必须有——工具链要求，照填，不省。

但要分清两件事：

| | 是什么 | 谁用 |
|---|---|---|
| 版本字段 | package 元数据里的一个必填项 | 工具链、发布 |
| 版本号 | 软件的版本 | 人看 |

- 系统插件**不单独发布**，所以没有任何解析器会去解它的版本。
- 填这个字段不是为了兼容，是为了工具链能跑。

## 3. 唯一源与同步

- 仓库根的 `VERSION` 是唯一手写版本号的地方。
- 其他 package 的版本字段由**脚本**同步：扫描 `VERSION` → 写进每个 package 的元数据。插件多到一定程度，人工手写不现实，也不该手写。
- 脚本：`scripts/sync_version.py`；断言测试：`app/boot/tests/test_version.py`。**约定会破，测试不会。**
- 现在只有 `VERSION` 是手写的；`pyproject.toml`、`package.json`、`app/ui-engine/package.json` 由脚本同步。

## 4. 协议和数据格式

- Python 与 TS 一起发，所以**协议没有独立版本号**。跨语言测试钉的是"两边是同一份协议"，不是"两边版本能对上"。
- 数据格式也跟着软件版本走。升级时系统插件和数据一起升；有迁移时，迁移脚本按软件版本编号。

## 5. 生态插件：暂不开放

我们不单独发插件：一起打包的都是系统插件，没有"可选系统插件"这一类。可选插件最多在文档里提一句，不提供发布物。
所以第 1 节的规则覆盖全部有发布物的插件；运行后安装只为一件事存在——将来的生态。

现在不考虑开放生态。开放的时候，规则是**接口一致就能用**：

- 不做版本范围声明，不做版本解析。
- 插件能不能用，只看它的接口面对不对得上：SDK 的形状、它要的服务名。
- 对不上就在装载时失败，不降级、不半跑。

代价要说清楚：**接口面本身就是兼容契约**。所以 SDK 要小、要稳、要可测；改一个方法名就是一次破坏性变更，哪怕没有版本号参与。

好处也说清楚：不做版本协商，失败发生在**装载时**，而不是运行中行为悄悄错掉。这是可以接受的失败方式。

## 6. 不做

- 每个插件一套独立 semver 加依赖范围。
- 系统插件之间声明 "requires core >= X"——它们本来就一起发，没有这种关系。
- 生态插件的版本范围声明与解析。
- 运行时按版本号分支：要判断能力就 `has()`，不用版本号。
