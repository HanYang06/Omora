# 配置设计

配置回答"这个软件是什么"：装哪些插件、开不开、监听哪、数据放哪。
它在启动期被读一次，运行期只读。

配置不是设置。设置是"用的人喜欢什么"，见第 6 节。

## 1. 两份文件

| | `config.ini` | `config.yaml` |
|---|---|---|
| 级别 | 系统级；约等于全局 | 用户级 |
| 来源 | 构建产物 | 用户手改 |
| 内容 | 全部配置的发行值 | 只写要覆盖的部分 |
| 形态 | 二进制，不可读 | 明文 |
| 谁写 | 没人；随包出去 | 用户 |

- `config.ini` 是构建出来的，不是手写的。源是各系统插件声明的配置项（第 4 节）。
- `config.yaml` 是唯一可改的入口。界面不能改它——界面也是插件，插件不能改自己的形态。

## 2. 合并

- **逐键深合并**：只写 `net.port` 就只改那一个键，其余沿用 ini。
- `config.yaml` 赢。
- 合并只做覆盖，不做创建：`config.yaml` 不能新增插件。要新增插件，装一个运行后插件。

## 3. 只读，启动期一次

顺序：读 ini → 读 yaml → 合并 → 构造插件对象 → 交给内核。

- 应用永远不写配置。运行期没有写入口。
- 改了要重启才生效。

## 4. 声明是源，ini 是产物

每个系统插件声明自己的配置项：键、类型、默认值、说明。构建时把所有声明合并，生成 `config.ini`。

- 二进制不可读因此不丢信息：仓库里那份声明是可评审的。
- 声明也是校验的依据：类型不对、键不存在，构建期就能发现。

## 5. 配置不决定有哪些插件

- 名单在代码里：boot 有一个有序列表。
- 配置只决定两件事：**默认开不开**、**参数**。生效开关由 manager 结合 store 里的用户设置决定，config 只是默认值。
- 顺序是代码属性，配置不能重排。
- 系统插件被配置关掉后，应用以降级形态起来。关掉某一个会怎样，由插件自己说清楚；不设"必需"标记。
- 配置不枚举插件、不校验插件。写了一个没有插件认领的段，它不会被读，自然不生效。
- 这个代价用可观测补：boot 装完之后报一次**没人认领的段**。这是回头看一眼谁没来领，不是让配置去决定谁存在。

## 6. 设置是另一条线

- 设置 = 用的人喜欢什么：主题、字号、默认视图。归插件自己，存哪、怎么改、界面怎么呈现，都是插件的事。
- 设置不改形态，不走配置的合并与覆盖机制。
- 目前已落的一处是**插件开关**：manager 把开关写进 store 的 `settings` collection（`plugin` / `enabled`），设置页改它，config.ini 只给默认值。见 [插件管理器](plugin-manager.md)。
- **不变量：设置不得写回 `config.yaml`。** 一旦为了省事让设置页把值落到配置里，形态就被运行期改了。

## 7. 没定的

- `config.ini` 的二进制格式（序列化方式）。
- 声明写成什么：插件类属性、单独的 schema 文件，还是别的。
- 插件开关已经定了（store 的 `settings`）；其余设置存在哪、怎么声明仍未定。
