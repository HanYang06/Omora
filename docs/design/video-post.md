# 视频后处理

摄像头是硬件下限，录下来那一刻只能接受；但录完之后手里是一整段文件，可以逐帧修正，
代价只是处理时间。这一层就是干这个的。

## 流程

```
上传的 WebM → media 读字节 → ffmpeg（降噪 / 去闪烁 / 提对比 / 锐化）→ H.264 MP4
→ media.save 新 id → 删掉原件 → capture 返回新 id
```

处理的顺序有讲究：

1. `hqdn3d` 时域降噪 —— 便宜镜头暗处噪点明显，先降噪；
2. `deflicker` —— 相机 3A 追光造成的亮度跳变，按帧窗口平滑；
3. `eq` + `unsharp` —— 轻微提对比 / 饱和 / 锐度，补一点镜头本身的软；
4. `libx264 -crf 23` 重编码。

先降噪再锐化，否则锐化会把噪点放大。

## 为什么用 CRF 而不是固定码率

码率是**结果**，不是目标。行业里做法是给编码器一个质量目标（CRF），让它自己决定哪一帧
多给比特、哪一帧少给；固定码率在简单画面上浪费、在复杂画面上又不够。所以我们把采集成
的码率开高（给后期留信息），落地用 CRF 收一遍——**观感更好、体积更小**。

## 失败怎么办

ffmpeg 失败（坏文件、缺库、磁盘满）时**保留原件**，返回原来的 media id，只记一条
`video.post_process.failed`。用户的录像不能因为后处理坏了就没了。

## 开关

`config.ini` 的 `[video]` 段可以关：

```ini
[video]
post_process = false
```

## 边界

- 拿到的是**压缩后的帧**，不是传感器 raw；后处理只能让画面"看起来更好"，不能补回没拍到的信息。
- 输出统一 H.264 / MP4：编码快、哪儿都能播、HTTP 通道按存的 mime 发。
- 转码是 CPU 活，720p 十秒大概几秒；和“录完立刻能看”之间是取舍，目前选的是处理完再落库。
