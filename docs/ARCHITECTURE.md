# Omora 架构

> 这份文件是事实来源：代码、测试、配置跟它冲突时，以它为准；要改它，先改它、再改代码。
> 只写已经定下来的；没定的明确标"未定"，不假装定了。

## 1. 它是什么

本地优先的灵感与项目管理工具：灵感、项目、需求互相可追溯。默认本地跑，也能部署成网页。

## 2. 两个进程，两个 runtime

| 进程   | 里面有什么         | 不做什么                 |
| ------ | ------------------ | ------------------------ |
| Python | 内核 + Python 插件 | 不碰界面                 |
| TS     | 渲染引擎 + TS 插件 | 不持有真相、不做领域判断 |

两边之间只有一条消息协议，由 net 插件（系统插件）持有并实现。内核不参与，也收不到帧。

两个进程一起发布，共用一个版本号。**系统插件的版本号 = 软件版本号**，不单独定版本（见 [版本设计](design/versioning.md)）。

分工的根据不是"哪个语言快"，是"代码必须跑在哪"：界面只能在 TS 进程；要成为唯一真相、要被服务端和多端共享的，只能在 Python 进程。

## 3. 内核

内核是 Python 进程里的插件宿主，只有四个词：

| 词   | 方法                    | 做什么                               |
| ---- | ----------------------- | ------------------------------------ |
| 加持 | `install`               | 装一个插件                           |
| 持有 | `running` / `names`     | 记着谁在                             |
| 引用 | `resolve`               | 按名字取服务                         |
| 运行 | `uninstall` / `dispose` | 跑 apply；卸载时逆序撤销它登记的一切 |

**内核提供"引用"这个能力，但不替任何人用。**

内核里没有：配置、消息帧、系统与运行后插件的分类、清单、能力授权、依赖图、槽位、组件、UI 校验、领域词。

- 依赖不归内核管。插件自己 `has('projects')` 判断，没有就自己处理。
- 插件登记的东西（服务、副作用）都记在内核的账本上，卸载按逆序撤销。
- 契约不是消息式的：进程内按名字拿到对象，直接调用。消息协议是 net 插件的事；把插件挪出进程时契约会变，这一版不做承诺。
- 并发不是内核的问题：服务方法会不会被并发调用，由分发它的人（net 插件）回答。
- 配置在 boot 里已经合并完、插件对象已经构造好，内核看不到配置。

整套东西里**唯一不是插件的，是 boot**：它站在所有插件外面，按代码里的有序列表构造插件。
它先装 `store` + `manager`，再把宿主服务（装 / 卸 / 名单）交给 `manager`，其余插件由
`manager` 按元数据条件与开关来装。boot 也不在内核里。见 [插件管理器](design/plugin-manager.md)。

## 4. Python 插件

一个插件 = 有名字、有 `apply(ctx)` 的对象。它能做两件事。

### 4.1 提供能力

`ctx.provide(name, value)` 登记服务。存储、领域规则、id、检索都这么来。别的插件按名字取，不 import。

### 4.2 贡献界面

插件产出一页的树（内容 + 标题旁那句话），用**页面对象**自己交上去；不产出界面的插件只登记服务。

- **推送式**：`ui.page(...)` 返回页面对象；`handle.set(tree)` 交树，状态变了再交一次。
- **重建钩子**：`handle.rebuild(build)` 登记重建回调——客户端明确要一页（导航 / 首次 render）时由 ui 调一次，
  用来吸收"插件后来才装上"这类外部变化。
- **只填自己的**：不改别人的树；想让别人挂东西，就在自己树里放一个有键的节点（`Slot(key=...)`）。
- **可介入**：别人按全限定键往那个位置挂（替换 / 前 / 后 / 进子节点），顺序是 `(order, owner, 声明序号)`。
- 键、贡献、组合的完整契约见 [UI 插件体系](design/ui-plugins.md)。

写法（界面库是 Python 包，内核不 import 它）：

```python
from omora.sdk.ui import Button, Column, Item, Page, Slot


class Ideas:
    def apply(self, ctx):
        self.page = ctx.resolve("ui").page(ctx, "ideas", "灵感")
        self.page.set(self.build())
        self.page.rebuild(self.build)

    def build(self) -> Page:
        return Page(
            meta=f"{len(self.store.items())} 条",
            content=Column(
                Slot(key="ideas.home.after_capture"),
                *[
                    Item(i.title, Button("归档", on_click=self.archive(i)), meta=i.when)
                    for i in self.store.items()
                ],
            ),
        )
```

序列化是通用的：节点是 `{type, props, children}`，按 dataclass 字段转，不给每个组件写 schema。回调登记成 id；渲染器把事件连 id 一起回传，插件跑函数、改状态、重新交树。

### 4.3 边界

- 插件只依赖插件 API（SDK），不 import 内核内部。
- 内核不 import 插件。
- 界面库是独立包，内核不依赖它。
- 插件之间的唯一通道是服务名。

## 5. 插件的两个维度

插件有两条正交的轴：**来源**决定它怎么发布、怎么升级；**语言**决定它能碰多深的界面。两条轴互不推导。

### 5.1 来源：系统 / 运行后

驱动这个区分的是**来源**，不是产出。

|            | 系统插件                               | 运行后插件 |
| ---------- | -------------------------------------- | ---------- |
| 来源       | 随发行包一起出去                       | 用户单独装 |
| 位置       | `packages/`                            | 待定       |
| 装不装     | 启动期的配置决定开关                   | 用户装     |
| 顺序       | 代码里的有序列表                       | 装的时刻   |
| 运行期     | 不可卸                                 | 随时装卸   |
| 缺了会怎样 | 应用以降级形态起来；后果由插件自己说清 | 少一个功能 |

产出页面不再是分类轴：系统插件和运行后插件都可能产出页面。对内核来说两者没有区别——它只认插件，不认来源。

系统插件里的 `manager` 持有插件清单、`[tool.omora]` 条件与开关（见
[插件管理器](design/plugin-manager.md)）。清单只决定"装不装"，不是权限系统。

**我们自己不单独发插件。** 一起打包出去的都是系统插件，而且没有"可选系统插件"这一说：要么在包里，要么不存在。可选的东西最多在文档里提一句"有这么个插件"，不给发布物。

运行后插件现在一个都没有。它就是将来的生态插件；开放之前，这一类是空的。

两件容易混的事分开说：

- **非可选是发行层面**：它一定在包里。
- **可关是配置层面**：配置仍然能关掉任意一个系统插件。关掉之后应用以降级形态起来，后果由插件自述。

"系统插件缺了应用就跑不起来"这句话不成立，所以也不设"必需"标记。

### 5.2 语言：决定能碰多深的界面

| 形态        | 写界面         | 写能力       | 界面边界                                   |
| ----------- | -------------- | ------------ | ------------------------------------------ |
| Python 插件 | 能：产出节点树 | 能：提供服务 | 只能挂到有键的位置，改不了别人的私有节点   |
| TS 插件     | 能             | 能           | 整套界面能力都归它                         |
| 混合插件    | 能             | 能           | 两个半边共用一份清单，各按自己那一侧的规则 |

语言不决定"写什么"，只决定"写出来的东西能伸到哪"。

- **Python 写界面是正路，不是退路。** 节点树由 Python 产出，TS 只负责画。
- **TS 写能力也是正路。** npm 生态摆在那，没有理由拦。但别在 TS 里存真相——server 形态没有 TS 进程。
- **混合插件没有额外规则。** 它就是把上面两条各走一遍；两边靠同一个名字对齐。

## 6. 渲染引擎与 TS 插件

渲染引擎在 `app/ui-engine/`：

- 组件注册表：节点类型 ↔ 组件。
- **组合器**：把若干份贡献挂在若干把键上，合成一棵 root tree（纯函数，见 [UI 插件体系](design/ui-plugins.md)）。
- 事件带 handler id 回传；id 里带归属，一页因此可以有多个 owner。
- 自带一个 TS 插件宿主（未做）：管 TS 插件，也管母页面。

### 窗口、页面与键

- **窗口**是引擎默认那层壳：它声明有哪些区域（现在两个：`om.window.nav` 图标栏、`om.window.page` 主区）。
- **页面**是一个可导航的根，挂在窗口的某个区域上；页面自己决定哪些节点有键。
- **贡献**是任意插件交来的一份树 + 落点键 + 顺序；一个键可以被多份贡献挂。
- **有键 = 可介入，没键 = 私有。** 这就是"固定组件 / 可替换组件"的唯一判据。
- 键全限定、全局唯一，第一段是声明者；构建期生成，作者不手写字符串。
- 顺序是全序 `(order, owner, 声明序号)`；同一个键上的 `replace` 走"后来者优先"。

组件词表是默认窗口的、核心的、有限的。够用靠组合；不够就加组件（不是换母页面）。

默认母页面是**三栏**：56px 图标栏（页面导航，每页一个图标）+ 主区。索引栏与主区由页面
自己用 `Split` 排，页面内容铺满主区，不再走 720px 居中的一页纸。区域、模式与词表见
[三栏首页](design/ui-home.md)。

## 7. 协议

一条消息协议，分两半看：

- **形状是合同**：帧长什么样、有哪些方向、错误怎么带。写在文档里，两边各实现一份，用跨语言测试钉住。
- **实现是 net 插件**：socket、编解码、分发、并发、推送队列，全归它（系统插件）。

形状不归插件管：对面是渲染引擎，不是插件。插件随时能换，合同不能。

- 上行：调用服务（名字 + 参数数据）。
- 下行：视图树（`result`）与主动推送（`event`）。
- 事件回传：handler id + 载荷。
- 订阅：客户端声明关心哪些 topic，net 只把订阅过的 `event` 发给它；断线即清空，重连由客户端重放。
- 增量：快照带版本号，变化走 `ui.snapshot` 补丁；对不上版本就重新要全量。
- 快照字段：`pages` / `page` / `meta` / `content` / `contributions`（可选）/ `topics`（可选）/ `version`。

规矩：

- 内核不认识帧，也不认识组件——它连帧都收不到。
- 只传数据，不传对象引用。
- 媒体字节不是帧：音频与视频都走 net 插件的 HTTP 媒体通道（`POST /media` 上传、
  `GET /media/{id}` 播放，见 [协议设计](design/protocol.md) §7）；帧里只有 media id。
  唯一例外是播放：`media.load` 仍按 base64 把字节还给渲染引擎（v0 形状，保留）。
  帧协议本身不变：只收文本帧。通道属于 net（它持有 socket），存盘属于 media 插件。
- 协议只有一份；两种语言各写一遍，用一个跨语言测试钉住。
- 服务会不会被并发调用、什么时候回帧，由 net 插件回答；能主动推这件事已经定了，形状在协议文档里。

双向已经开了半边：帧允许 `call` 从任一侧发，TS → Python 已经通了，Python → TS 用 `event` 推。
未定的是反向**调用**：Python 侧要拿 TS 的能力（剪贴板、窗口控制）得等 TS 宿主也有服务表；
而且 Python 服务方法是同步的，里面不能 await 一次跨进程往返。

## 8. 运行形态

- App：Python 进程 + TS 进程。
- Server：只有 Python 进程；没人拉视图，就不构造。

插件是否独立进程：先跑在 Python 进程内。要崩溃隔离或者要跑别的语言时再挪——那时契约会变（进程内拿的是对象），这一版不为此提前设计。

视频落库前会过一遍后处理（降噪 / 去闪烁 / CRF 重编码），见 [视频后处理](design/video-post.md)。

日志：两个进程、一条时间线。内核是唯一写者，渲染引擎把日志攒批送到 `log` 服务的
`write_many`，内核统一落盘与上屏；通道与开关见 [日志与观察性](design/logging.md)。

## 9. 混合插件

一个插件同时有 Python 和 TS 两半：**一份清单，若干半边**。清单声明它有哪些半边（Python 入口 / UI 入口），
内核加载 Python 那半，引擎加载 UI 那半，两边用同一个插件 id 对齐。

纯 UI 插件也合法（只有 UI 半边）：它的界面可以存在，数据只能向 Python 服务要，server 形态没有它。
清单格式与加载实现见 [UI 插件体系](design/ui-plugins.md) §11。

## 10. 代码在哪

| 位置             | 是什么                                                          | 语言    |
| ---------------- | --------------------------------------------------------------- | ------- |
| `app/core/`      | 内核：插件宿主（四个词）；package `omora-core`                  | Python  |
| `app/sdk/`       | 插件 API（SDK）：Context / Plugin / UI 节点 / 协议；`omora-sdk` | Python  |
| `packages/`      | 系统插件：`omora-plugin-*`，uv workspace 的 member              | Python  |
| `app/ui-engine/` | 渲染引擎 + 桌面壳：组件注册表、贡献组合、事件                   | TS / JS |
| 运行后插件目录   | 单独装、可卸的插件                                              | 待定    |
| `docs/`          | 事实来源，架构文档在这里                                        | —       |

## 11. 落地顺序

1. 内核 + 测试（`app/core/`）。已落。
2. boot + 配置：读两份配置、合并、构造插件、报没人认领的段。已落。
3. net 插件 + 最小协议 + 一个系统插件 + 最小渲染引擎：列表画出来，按钮点得动。已落。
4. 界面库 + 第一个槽位：灵感。已落。
5. 领域插件：灵感 / 项目 / 需求，按需要长，不按表拆。已落。
6. 插件管理器：清单、`[tool.omora]` 条件、开关落 store、设置页。已落。
7. 第二个插件证明组合；最后才是 server 形态。

## 12. 明确不做

信任分层、依赖图、契约三件套、多阶段门禁、C / Rust 内核、插件进程化、配置热更新、界面改配置、设置与配置合并、生态开放——等真疼了再说。

清单与平台 / 能力条件已经做了，但它只回答"这个宿主装不装"，不是权限或授权系统。

生态开放的时候只有一条：**接口一致就能用**，不做版本范围解析。
