# P1：从「能跑」到「能用」

> 前置：P0 证明了架构能跑（一个插件能通过 C1 / C3 在界面上画出面板，数据来自内核）。
> P1 要证明的是另一件事：**它值得每天打开。**

## 1. 三个使用时刻

产品不从这里出发就会长成一堆功能。Omora 只有三个时刻值钱：

| 时刻 | 场景 | 界面 | 判据 |
|---|---|---|---|
| 捕捉 | 想到什么，3 秒内扔进去，不切窗口、不被要求分类 | 收件箱 | 从念头到落库 ≤ 3 秒，不需要鼠标 |
| 推进 | 某个想法值得做，它变成项目里的需求，状态往前走 | 项目 | 一天里大部分时间在这一屏 |
| 回看 | 为什么做这件事？它从哪个念头来的？ | 追溯 | 任意需求能追到源头，不靠记忆 |

**推导出 P1 的范围：收件箱、项目、需求、关联、检索。其余一律不做。**

## 2. 做

- **收件箱**：一条输入框，回车即存；列表可编辑、归档、分诊到项目
- **项目**：项目列表、项目详情、项目下的需求
- **需求**：新建、改状态、归属项目
- **关联**：灵感可以挂到项目上（分诊），并保留来源
- **检索**：按标题跨实体模糊搜索
- **壳**：侧边栏（收件箱 / 项目）、主区、命令面板（Cmd / Ctrl + K）

## 3. 不做（连同理由）

| 不做 | 理由 |
|---|---|
| 多用户、权限 | 需要服务器形态与信任模型，P3 |
| 同步、CRDT、Git | 同上；本地优先先把本地做扎实 |
| 移动端 | 需要独立的触摸交互设计 |
| 看板 / 甘特 / 时间线 | 复合控件，等 P2 的控件注册表 |
| 导入导出 | 无损往返是独立工程 |
| 主题 / 快捷键系统 | 机制先于内容，P2 |
| AI 助手 | 没有稳定的数据模型之前接 AI 只会更乱 |

## 4. 硬约束（这才是 P1 的真正目的）

P1 不是「加功能」，是**用功能去反推核心 API**。所以：

1. 所有新功能必须由官方插件通过 C2 / C3 实现，内核只出现机制；
2. 内核零领域词汇：出现 `Project` / `Requirement` / `Task` 就是边界破了；
3. 跨插件能力只能走服务注册表，插件之间不许互相 import；
4. 契约只加不改，破坏性变更走主版本。

**写不顺的时候，结论不是「给内核开个后门」，而是「补 API」。**

## 5. 里程碑

| 里程碑 | 内容 | 验收 |
|---|---|---|
| P1.1 | 插件查询注册、服务注册表（插件间调用） | 插件能注册查询；A 能调用 B 提供的服务，B 卸载后 A 得到可处理的失败 |
| P1.2 | projects 插件 | 建项目、列项目，列表可渲染 |
| P1.3 | requirements 插件 | 需求挂在项目下，状态可流转 |
| P1.4 | ideas 插件升级 | 编辑、归档、检索、分诊到项目（经服务调用） |
| P1.5 | 壳与设计 | 侧边栏、主区、命令面板、空状态 |
| P1.6 | 验收 | 捕捉 → 分诊 → 建需求 → 改状态 → 回看，全链路可走 |

### 暂不做

| 项 | 原因 |
|---|---|
| 全局检索 | 状态已经完整投影到前端，本地过滤是小事；但"搜到之后能做什么"取决于选择与跳转模型，那是 P2 的设计问题。先不做半截体验 |
| 需求回溯到来源灵感 | 需要选择与跳转模型；当前 `ideas.assign` 已经记录了归属，反向链接等 P2 |
| 引用选择器（挑一个项目来分诊） | 需要新的 C3 控件（Select）。控件词表扩张要谨慎，留给 P2 的控件注册表 |

## 6. 怎么判断 P1 有没有做对

不看演示，看三条：

1. 新功能的 diff 是不是**只动了 `plugins/` 与 `web/`**？内核的改动是不是只有机制？
2. 卸载任意一个插件，其余功能是否仍然完整？
3. 加第三个插件时，**有没有被迫改内核**？

三条都过，说明这层 API 是真的；任何一条不过，说明抽象漏了，回去补 API 而不是补特例。
