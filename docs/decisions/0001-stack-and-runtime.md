# ADR-0001：运行时与技术栈

- 状态：已接受
- 日期：2026-11-06
- 相关：ADR-0002、architecture/overview.md、architecture/contracts.md

## 背景

产品需要同时满足：

1. 多形态运行：本地桌面 App + 可部署到服务器的 Web。
2. 一切皆插件：核心极小，功能由插件提供。
3. 插件能修改 UI，但方式是调用与声明，而不是创建 UI。
4. 社区自发传播插件，没有官方市场。
5. 与 GitHub / GitLab 互通，但不绑定任何一方，也不依赖它们。
6. 灵感需要即时捕获：冷启动快、离线可用、本地优先。

现实约束：

- 维护者以 Python 为最舒适语言，同时接受 TypeScript，拒绝纯 JS 风格。
- 前端技术不可放弃——放弃 Web 渲染层，UI 质量直接崩。
- 性能不是首要矛盾；IPC 与多进程可以接受。
- 希望第二门语言（Rust 或 C#）能在这个项目中练手。

## 决策

1. **内核用 Python**：领域模型、存储、事件日志、权限、插件宿主、AI/数据能力、Git 适配全部归内核。
2. **前端用 TypeScript**：声明式渲染器 + 组件词表 + 壳；不写业务判断。
3. **中间是协议，不是共享内存**：C1（内核↔前端，私有）、C2（宿主↔插件，公开）、C3（插件↔渲染器，公开数据 ABI）。
4. **UI 贡献是数据**：插件产出一棵声明式节点树，渲染器负责画。因此 UI 插件不产生进程。
5. **插件默认 Python**，与内核同进程、按 scope 隔离；异语言插件走进程池或 WASM 池，协议不变。
6. **本地 SQLite 是规范主副本**，追加事件日志是其变更流的来源；「存到 NAS / OSS / 服务器」实现为复制目标插件。
7. **Git 不自研**：核心只提供服务注册与能力路由，git 服务由官方插件提供。
8. **桌面壳后置**：P0 只做本地 Web（Python WS + 浏览器），桌面壳是后续包装。

## 后果

正面：

- 每件事落在它的主场：逻辑归 Python，界面归 TS。
- 「能支持多少种语言」由协议决定，与内核语言解耦。
- 插件数量增长不会带来进程数量增长（UI 插件是数据）。
- 官方功能与第三方插件同门同 API，生态是真的。

负面：

- 永远维护两套工具链（uv / pnpm）。
- 桌面形态需要 Python sidecar，是最脏的一块，必须后置。
- C1 边界成为产品级资产，设计失误会全盘返工。

中性：

- Rust / C# 不进入核心，短期以插件语言身份存在；Rust 的正式位置（壳、WASM 宿主、高性能组件）留到 P2。

## 备选方案

| 方案 | 不选的理由 |
|---|---|
| 全 TS 内核 + Cordis | 开发最统一，但把维护者的主要舒适区让掉了；AI/数据类能力在 TS 里是二等公民 |
| 纯 Python UI（Tk / Qt / Flet / NiceGUI） | 天花板正好卡在最核心的卖点：插件声明式改 UI |
| Rust 内核 + WASM 插件宿主 | 隔离最强、单二进制，但双语言 + 迭代慢，产品定义尚未收敛 |
| C# / .NET 内核 | 没有结构性位置：要么和 Python 抢同一块地，要么只是一门插件语言 |

## 复查触发条件

- 维护者认为「日常写 TS」不可接受 → 回到 Python 内核（但渲染层仍是 TS）。
- 服务器 v1 就要求多租户不可信插件 → WASM 沙箱前置，Rust 变必需。
- 插件生态主力被证明是 Python 人群 → 重新评估默认语言档位。
