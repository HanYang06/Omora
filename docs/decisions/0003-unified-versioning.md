# ADR-0003：统一版本发布

- 状态：已接受
- 日期：2026-11-06
- 相关：ADR-0001、architecture/contracts.md 第 0.5 节

## 背景

多包独立版本会带来三个必然结果：兼容矩阵、版本错配、测试组合爆炸。对单人维护的项目，这三件事都不可持续。

维护者要求：仓库内所有部分**版本号始终统一**——要么不更新，更新则整体前进，不允许某一部分单独走号。

## 决策

1. **同号发布**：内核、前端、协议定义、官方插件，一律使用同一个版本号。
2. **语义即承诺**：
   - PATCH：契约不变；
   - MINOR：契约只加不改；
   - MAJOR：契约可破。
3. **主版本号只用于契约破坏**，不得用于产品营销。
4. **单一版本源 + CI 校验**：任何包版本不一致，构建失败。不校验的统一版本等于独立版本。
5. **第三方插件仍有自己的版本**，通过 `engines` 声明对宿主版本的范围，宿主用 semver 校验。
6. **0.x 阶段不提供兼容承诺**：起始版本定为 `0.1.0`，插件收紧到 `0.3.x` 这类写法；对外正式开放插件生态时定 1.0。

## 后果

正面：

- 消灭版本矩阵：用户只认一个版本号。
- 升级路径单一：不存在「内核升了但前端没升」。
- 契约兼容规则内建在 semver 里，不需要额外维护一套契约版本号。

负面：

- 任一处改动都会触发全量发布（monorepo 下成本很低，但要接受）。
- 主版本号承载契约语义，纪律要求高：一次「营销式大版本」就会让所有插件拒绝加载。

中性：

- 官方插件与内核同号；第三方插件独立版本。

## 备选方案

| 方案 | 不选的理由 |
|---|---|
| 独立版本 + 兼容矩阵 | 维护成本高，单人不可持续 |
| 统一号 + 独立契约号 | 多一层映射，正是要消灭的东西 |
| 统一号但不校验 | 退化为手工同步，实质上仍是独立版本 |
