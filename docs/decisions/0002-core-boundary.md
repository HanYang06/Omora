# ADR-0002：核心与插件的边界

- 状态：已接受
- 日期：2026-11-06
- 相关：ADR-0001、architecture/core-surface.md

## 背景

「一切皆插件」不等于「没有核心」。任何插件系统都有一个不可再分的引导底座。问题不在于要不要核心，而在于**核心的准入标准是什么**——没有标准，核心会在半年内自己长回来。

## 决策

1. **三道测试**：一个能力必须是核心，当且仅当满足至少一条——引导性（插件加载前就要在）、信任性（交给插件执行等于没执行）、契约性（它本身就是共享契约）。三条都不满足 → 插件。
2. **核心是七个子系统**：启动与装配、执行单元、信任、契约、状态、界面运行时、运维。清单见 core-surface.md。
3. **零领域词汇**：核心代码中出现 Idea / Project / Kanban 等业务概念，视为边界破坏。
4. **官方无后门**：所有官方功能必须用公开的 C2 / C3 实现；写不出来 = 核心 API 缺能力，补 API，不许开后门。
5. **准入 RFC + 季度瘦身**：新增核心能力需一页纸过三道测试；每季度反向扫描，能下放的全部下放。

## 后果

正面：

- 核心长期可控，不会随功能增长而膨胀。
- 插件 API 被官方功能持续压测，不容易变成假的。
- 第三方与官方能力对等。

负面：

- 部分官方功能会比「直接写核心」慢一拍。
- 需要持续维护边界纪律，靠人自觉不够，要靠评审。

## 备选方案

| 方案 | 不选的理由 |
|---|---|
| 核心更大，把常用能力都放进去 | 半年后无法收缩；第三方永远追不上默认体验 |
| 核心更小，连插件宿主都做成插件 | 引导链变脆；加载器本身出错时无自举能力 |
| 不设边界，按需决定 | 边界会由最省事的那次提交决定，而不是由设计决定 |
