# 路线图

> 只写**方向、阶段、退出条件与止损条件**。完成记录在 [changelog](changelog.md)，未完成工作在 [TODO](todo.md)。
> 时间尺度：**现期 2 周 / 近期 2 月 / 长期 3 月（累计第 6 个月）/ 展望 1 年+**。基线 2026-11-18。
> 现状与证据见 [项目现状](planning/state-of-project.md)；目标架构见 [V1 树](planning/v1-tree.md)；怎么定方向见 [决策机制](planning/decision-process.md)。

## 0. 定论

> **引擎先完善，产品闭环随后。**
> 理由只有一条：引擎半途而废，业务迁移成本会翻倍；现在产品只有一页，是换地基最便宜的时候。

三句话：

1. **引擎核心必须做完。** 静态结构 + 最小节点更新 + 协议 + 页面插件迁移 + 旧路径删除 + 复杂度护栏。非核心（组件补齐、规则执行、远程来源）随业务与维护补，不单独排期。
2. **产品不是消失，是后置。** 长期做 Idea 闭环 + Project 闭环；需求（requirements）最后。
3. **每条轨道有到期日。** 第二实现、实验、迁移，都要有结论，不许变成默认背景。

### 引擎核心 / 非核心

| 类别   | 内容                                                                   | 处理               |
| ------ | ---------------------------------------------------------------------- | ------------------ |
| 核心   | 静态结构、最小节点更新、ops 协议、页面插件迁移、旧路径删除、复杂度护栏 | 近期必须做完       |
| 非核心 | 组件词表、规则执行、远程来源、订阅 / 媒体登记、集合嵌套、权限细项      | 业务推进时顺带维护 |

## 1. 现期：定基与第一段（2026-11-18 → 2026-12-02）

**目标**：把目标架构写成决定，把第一段路径跑通。

- 文档与队列定基：ADR-0004、本路线图、项目现状、决策机制、TODO。
- 冻结 ops 形状与跨语言 fixture。
- 真实页面构建期 compose：先 ideas。
- ideas 一页端到端：Python 只发变更节点 → 协议 → TS 应用 → DOM 只 patch 变更。

**退出条件**：

- 一个真实页面走新路径，事件不再整树重建。
- ops 帧有跨语言 fixture；版本不匹配能全量兜底。
- 复杂度斜率可测：事件 → DOM 不随总节点数增长。

**止损**：协议语义 12-02 定不下来，就只做 home 模式，整页迁移进近期；不半接、不双路径并行。

## 2. 近期：引擎完善（2026-12 → 2027-02）

**目标**：引擎核心做完，插件迁完，旧默认路径删除。

- 静态结构覆盖全部页面。
- 最小节点更新成为唯一主路径；全量只作兜底。
- 页面插件迁移：ideas / projects / requirements / manager。
- 删除 Slot 默认路径；旧路径不再可进入。
- 复杂度护栏进 CI。
- 0.2 发布：冻结 schema + 迁移 runner + 一条真实迁移 + 安装包。

**退出条件**：默认入口只走 V1；事件 → DOM 不随总节点数增长；旧路径删除；四个页面插件全部迁移；0.2 有 tag、安装包与迁移；全量门禁绿。

**止损**：某个插件迁不动，保留它的 Slot 路径并记 ADR，不阻塞其余；不为单个插件拖住整体。

## 3. 长期：Idea 闭环 + Project 闭环（2027-02 → 2027-05）

**目标**：两个闭环形成基本架构。需求（requirements）后置。

**Idea 闭环**：

- 记下：文字 / 语音 / 视频，录了即存。
- 整理：搜索、标签、置顶、归档。
- 关联：灵感 ↔ 灵感、灵感 ↔ 项目。
- 用上：转写进搜索；从项目反查来源。

**Project 闭环**：

- 建项目 → 关联灵感（需求后置）→ 状态推进 → 归档 / 复盘。
- 从项目能看见它的灵感来源；从灵感能看见它去了哪个项目。

**退出条件**：一条灵感从记下到被项目用上，不离开 Omora；一个项目从 0 到归档，来源可追溯；重启不丢；0.2 已发布，升级不丢数据。

**止损**：闭环需要引擎新能力时，先记 ADR，不在业务里绕。

## 4. 展望：长期维护与领域插件（2027-05 → 1 年+）

引擎稳定后，长期是两件事：维护，和在部分领域插件里试新东西。

候选尝试（不承诺，按真实痛点决定）：

- **AI 开发**：提升 AI 辅助开发的上限，不只是补全。
- **架构设计**：把架构设计、组织结构的知识做成能力。
- **邮件聚合**：多账号统一收件箱，主邮箱回复。

邮件这条值得单独说：很多开发者手上两三个、三四个邮箱，通知分散、信息难统合；现有软件要么收费，要么大公司不做这种小场景；“收件箱聚合”很多企业软件也不做。用户不关心是哪个账号发的，关心邮件本身，由主邮箱回过去就行。这是典型的“小场景、真痛点、适合插件”。

判断标准：真实痛点、能做成插件、不破坏本地优先。三条都满足才做；不满足就留在文档里。

## 5. 横切规则

- 引擎核心由**真实页面**验收，不由能力清单验收。
- 第二实现 / 实验 / 迁移：三个问题 + 一个结论文档 + 一个到期日。
- 默认入口唯一。
- 每两周复盘：闭环能否走通、文档漂移、队列健康。
- 文档单一状态源。

细则见 [决策机制](planning/decision-process.md)。

## 6. 非目标

- 多人协作 / 房间 / 实时协同。
- 云同步。
- 移动原生 App（先做浏览器端）。
- 生态开放 / 插件市场。
- React 式函数组件、hooks、JSX、隐式重跑。
- 插件版本范围解析。
- 在没有页面需要前扩组件词表。
- 需求（requirements）不是当前重点。
