# 工程纪律

> 地位：与架构文档同级。违反纪律的改动不合并，不管功能是否"能用"。
> 生效：已生效（P0-0 完成，门禁全绿；反向验证通过）。门禁没绿之前，不写业务代码。

## 0. 设计目标

让"装作完成"无法通过。

纪律不是为了显得专业，而是为了堵住已知的翻车方式。下面每一条都能对应到一个具体的失败模式。

## 1. 常见翻车 ↔ 对应纪律

| 常见翻车 | 对应纪律 |
|---|---|
| 声称测试通过，其实没跑 | 完成定义要求附命令与输出 |
| 改测试迁就实现 | 测试纪律：先证明测试错，再改 |
| 过度抽象、提前设计 | 变更纪律：先最小实现 |
| 依赖乱加、供应链膨胀 | 依赖政策：标准库优先，新增需理由并登记 |
| 顺手改无关文件 | 一次提交一件事 + 自查 diff |
| 偷偷改契约 | schema 唯一真相 + changelog 契约段 |
| 边界腐烂（核心长出业务） | 架构测试机械执行 |
| 静默失败、假装成功 | 失败处理：必须报告，禁止掩盖 |

## 2. 门禁：唯一入口

**本地与 CI 必须跑同一条命令**，否则纪律是假的。

```
uv run python scripts/check.py
```

它按顺序执行下列阶梯，任一失败立即停止：

| 阶梯 | Python | TypeScript |
|---|---|---|
| 仓库卫生 | `scripts/check.py` 内置扫描 | 同左 |
| 体量预算 | `scripts/check.py` 内置 | 同左（eslint 读同一份 budget.json） |
| 格式化检查 | `uv run ruff format --check .` | `pnpm exec prettier --check .` |
| Lint | `uv run ruff check .` | `pnpm exec eslint .` |
| 类型检查 | `uv run pyright` | `pnpm exec tsc --noEmit` |
| 单元测试 | `uv run pytest -q` | `pnpm exec vitest run` |
| 契约测试 | `uv run pytest -q tests/contract` | `pnpm exec vitest run tests/contract` |
| 架构测试 | `uv run lint-imports` | eslint boundaries 规则 |
| 构建 | `uv build` | `pnpm build` |

规则：

- 禁止跳过阶梯；禁止 `--no-verify`。
- `# type: ignore` 与 `eslint-disable` 必须带错误码与理由，否则视为失败。
- 检查红着就提交，视为没有交付。

## 3. 架构测试（机械执行，不靠自觉）

| 规则 | 执行方式 |
|---|---|
| 内核不得 import 插件 | import-linter forbid |
| 官方插件只能 import `omora_sdk` | import-linter forbid |
| 核心零领域词汇 | 源码扫描禁用词表 |
| 前端只能经 `rpc` 访问内核 | eslint no-restricted-imports |
| `protocol` schema 是唯一真相 | 重新生成后 `git diff` 必须为空 |
| 所有 RPC 消息过 schema 校验 | 契约测试 |
| 事件必须可重放 | emit → replay → 投影一致 |

禁用词表（仅扫描内核源码）：`Idea` `Project` `Requirement` `Kanban` `GitHub` `GitLab`。
例外必须写进测试的 allowlist，并注明理由；不允许"加个 ignore"绕过。

## 4. 契约纪律

- `protocol/` 下的 schema 是唯一真相；Python 与 TS 的类型由它生成或校验。
- 改契约必须**三件套一起做**：schema、生成物、changelog 的 contract 段。少一件就是没改完。
- 破坏性变更必须先有 ADR，并按 ADR-0003 走主版本号。
- 未知字段默认拒绝，不静默忽略。
- 保留上一版的 fixture，新代码必须能读旧消息（兼容性测试）。

## 5. 测试纪律

- 新模块必须有测试；bug 修复必须先有回归测试。
- 每个公开方法至少一个测试；每种事件至少一个往返测试。
- 契约层用 golden file 固定 JSON 样本，不接受"跑一遍看看"。
- 测试必须可重复：不依赖真实时间、网络、随机、当前目录。时间、ID、随机数从注入的钟取。
- 慢测试打标记并默认隔离。
- 不追覆盖率数字，但**改动的行为必须被测试覆盖**。

## 6. 变更纪律

- 一次提交只做一件事；重构与功能分开提交。
- 先写最小可验证实现，再抽象；禁止提前抽象。
- 依赖政策：标准库优先；新增三方依赖必须写理由，并记录到 `docs/engineering/dependencies.md`。
- 锁版本，锁文件入库。
- 禁止提交：注释掉的代码、调试打印、无 issue 号的 TODO、密钥、生成物（生成类型与锁文件除外）。

## 7. Git 与版本

- 完整规则见 `.agents/skills/omora-git/SKILL.md`（格式、字数、分支、PR、合并方式）。
- 主干始终可运行；分支短命。
- 提交信息：`type(scope): subject`，type ∈ `feat` `fix` `refactor` `test` `docs` `chore` `contract`。
- 提交前自查 diff：有没有无关改动、有没有调试残留。
- CI 红不合并；不允许强推主干。
- 版本号单一来源：根目录 `VERSION`；CI 校验所有包同号（ADR-0003）。

## 8. 文档纪律

- 行为或契约变化，必须在同一次提交里更新文档。
- 决策写 ADR；不写 ADR 的决策视为没发生。
- 每次发版更新 changelog，必须有 contract 段（写"无变化"也算）。

## 9. 完成定义（Definition of Done）

- [ ] 改动范围与任务一致，没有顺手修改
- [ ] `scripts/check.py` 全绿
- [ ] 有测试，且测试证明了行为（不是只跑通）
- [ ] 契约未变；若变，schema + 生成物 + changelog +（破坏时）ADR 齐全
- [ ] 相关文档已同步
- [ ] 无 TODO、无调试残留、无死代码
- [ ] 已附证据：命令 + 输出摘要
- [ ] 未验证的部分已明确标注

## 10. 失败处理

- 测试失败不得跳过、不得改测试迁就实现。
- 无法验证的内容，必须写明"未验证"及原因，不得伪装成已验证。
- 阻塞时报告阻塞点并给选项，不猜需求继续做。

## 11. 纪律的成本

每条规则都必须挡住一个真实会发生的错误；挡不住的规则删掉。

纪律的成本如果长期高于返工成本，它就会被绕过——那时应该改纪律，而不是假装它还在生效。早期允许的放宽项（例如 e2e 推迟到 P1）必须写进这里，而不是悄悄不做。

### P0 明确放宽的项

写在明处，不是悄悄不做：

| 项 | 现状 | 何时收紧 |
|---|---|---|
| C1 入站帧校验 | 手写规则 + 与 schema 对拍的校准测试（23 条边界） | 出现第二种语言的客户端时改成 schema 驱动 |
| 传输背压 | 队列溢出即断开，策略与理由写在代码注释里；未做压力测试 | 有服务器部署形态时 |
| 插件惰性激活 | 只实现 `onStartup`；`onCommand` / `onEvent` 仅校验不生效 | P1 |
| 能力授权执行 | 只校验清单声明，不拦截调用 | 引入第三方插件之前 |
| 端到端 | 由 `scripts/accept_p0.py` 驱动真实内核，不进单元测试阶梯 | 保持：e2e 不该进快阶梯 |
| 前端视觉 | 渲染器有单元测试，页面未人工验收 | 有设计稿之后 |

## 12. 体量预算

预算写在 [budget.json](../../budget.json)：**单一真相**，门禁与 eslint 都读它。

| 维度 | 默认 | 说明 |
|---|---|---|
| 单文件行数 | 300 | 文档 400；组件 220 |
| 单函数行数 | 60 | 上帝组件的第一道防线 |
| 单类方法数 | 15 | 上帝对象 |
| 参数个数 | 5 | 参数一多，说明职责没拆 |
| 圈复杂度 | 12 | |
| import 数 | 20 | 依赖过多通常意味着职责过多 |

规则：

- 预算不是建议，是门禁。**超了就拆，不要改预算。**
- 改预算必须在提交说明里写理由。
- 例外只能在 `budget.json` 里按路径声明，禁止行内 ignore。
- 文档同样有预算：文档不是越长越好。
