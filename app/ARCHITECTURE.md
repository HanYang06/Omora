# Omora 架构

> 这份文件是事实来源：代码、测试、配置跟它冲突时，以它为准；要改它，先改它、再改代码。
> 只写已经定下来的；没定的明确标"未定"，不假装定了。

## 1. 它是什么

本地优先的灵感与项目管理工具：灵感、项目、需求互相可追溯。默认本地跑，也能部署成网页。

## 2. 两个进程，两个 runtime

| 进程 | 里面有什么 | 不做什么 |
|---|---|---|
| Python | 内核 + Python 插件 | 不碰界面 |
| TS | 渲染器 + TS 插件 | 不持有真相、不做领域判断 |

两边之间只有一条消息协议。内核只转发，不解析内容。

分工的根据不是"哪个语言快"，是"代码必须跑在哪"：界面只能在 TS 进程；要成为唯一真相、要被服务端和多端共享的，只能在 Python 进程。

## 3. 内核

内核是 Python 进程里的插件宿主，只有四个动作：

| 动作 | 做什么 |
|---|---|
| 加持 install | 装一个插件并运行 |
| 持有 hold | 记着谁在、谁提供了什么 |
| 运行 run | 执行插件的 apply；卸载时撤销它登记的一切 |
| 引用 resolve | 按名字取服务 |

再加一件：消息转发。

内核里没有：清单、能力授权、依赖图、槽位、组件、UI 校验、领域词。

- 依赖不归内核管。插件自己 `has('projects')` 判断，没有就自己处理。
- 插件登记的东西（服务、副作用）都记在内核的账本上，卸载按逆序撤销。
- 契约是消息式的：名字 + 数据，不传对象引用。所以将来内核换语言、或插件挪出进程，契约不用改。

## 4. Python 插件

一个插件 = 有名字、有 `apply(ctx)` 的对象。它能做两件事。

### 4.1 提供能力

`ctx.provide(name, value)` 登记服务。存储、领域规则、id、检索都这么来。别的插件按名字取，不 import。

### 4.2 贡献界面

返回一棵节点树，填进壳定义好的固定槽位。

- 只填自己的：不改别人的树、不发明槽位、不需要知道还有谁在。
- 拉取式：渲染器要哪个视图才构造；没有渲染器就没人调 `view()`。
- 槽位先来先得，不预先设计一套体系。

写法（界面库是 Python 包，内核不 import 它）：

```python
from omora.ui import Column, Row, Text, Input, Button

class Inbox:
    def view(self):
        return Column(
            Text("收件箱", kind="title"),
            Input(placeholder="记一笔", on_submit=self.capture),
            *[Row(Text(i.title), Button("归档", on_click=self.archive(i)))
              for i in self.store.ideas()],
        )
```

序列化是通用的：节点是 `{type, props, children}`，按 dataclass 字段转，不给每个组件写 schema。回调登记成 id；渲染器把事件连 id 一起回传，插件跑函数、改状态、回一棵新树。

### 4.3 边界

- 插件只依赖插件 API（SDK），不 import 内核内部。
- 内核不 import 插件。
- 界面库是独立包，内核不依赖它。
- 插件之间的唯一通道是服务名。

## 5. 渲染器与 TS 插件

渲染器在 TS 进程：

- 组件注册表：节点类型 ↔ 组件。
- 渲染固定槽位，按顺序摆各插件的贡献。
- 事件带 handler id 回传。
- 自带一个 TS 插件宿主：想接管整个界面的插件住这里，自己负责渲染槽位（或者不渲染）。

组件词表是核心的、有限的。够用靠组合；不够就得改渲染器。

## 6. 协议

一条消息协议，两个方向：

- 上行：调用 Python 服务（名字 + 参数数据）。
- 下行：视图树、事件。
- 事件回传：handler id + 载荷。

规矩：

- 内核不解析 UI 数据，也不认识组件。
- 只传数据，不传对象引用。
- 协议只有一份；两种语言各写一遍，用一个跨语言测试钉住。

## 7. 运行形态

- App：Python 进程 + TS 进程。
- Server：只有 Python 进程；没人拉视图，就不构造。

插件是否独立进程：先跑在 Python 进程内。契约已经按 IPC 写好了；要崩溃隔离或要跑别的语言时，把插件挪出去——改的是加载方式，不是契约。

## 8. 混合插件（未定）

一个插件同时有 Python 和 TS 两半（例如 Python 提供领域服务、TS 提供一个自定义整屏），需要一个跨两个宿主的身份。

现在不设计。只留口子：内核的插件身份稳定；渲染器能按同一个 id 加载 TS 那一半。等第一个真实需求。

## 9. 落地顺序

1. 内核 + 测试。
2. 最小协议 + 一个 Python 插件 + 最小渲染器：列表画出来，按钮点得动。
3. 界面库 + 第一个槽位：收件箱。
4. 领域插件：灵感 / 项目 / 需求，按需要长，不按表拆。
5. 第二个插件证明组合；最后才是 server 形态。

## 10. 明确不做

清单、能力授权、信任分层、依赖图、槽位体系、契约三件套、多阶段门禁、C / Rust 内核、插件进程化、混合插件——等真疼了再说。
