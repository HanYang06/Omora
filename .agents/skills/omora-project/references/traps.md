# 已知反模式

> 每条都对应一个真实会发生的翻车方式。看到症状，按"正确做法"处理；能机器拦的已经在门禁里。

| 反模式 | 症状 | 正确做法 | 机器怎么拦 |
|---|---|---|---|
| 假装完成 | "应该可以""理论上没问题" | 附命令与输出；跑不了就说没验证 | 完成定义 + 评审 |
| 改测试迁就实现 | 测试红了就去改断言 | 先证明测试本身错，再改，并写明理由 | 评审 |
| 核心长出业务 | 内核里出现 Idea / Project / Kanban | 挪到插件；补 SDK 能力 | 架构测试 + `budget.python` |
| 官方插件开后门 | 插件 import 内核内部模块 | 只依赖 `omora_sdk`；缺能力就补 API | import-linter |
| 前端直连内核 | `web/src` 直接 import 内核代码 | 只能经 `rpc/` 层 | eslint no-restricted-imports |
| UI 做业务判断 | 组件里算权限、算状态流转 | 判断回内核，UI 只展示 | 评审 + 架构 |
| 偷偷改契约 | 加了字段但 schema / changelog 没动 | schema + 生成物 + changelog 三件套 | 契约测试 + 评审 |
| 上帝组件 | 一个文件几百行、一个函数几十个分支 | 拆职责；先拆数据与交互 | `budget.files` / eslint |
| 上帝对象 | 一个类几十个方法 | 按职责拆成多个服务 | `budget.python` |
| 提前抽象 | 还没第二个用例就造框架 | 先最小实现，出现第二次再抽象 | 评审 |
| 依赖乱加 | 能标准库解决却引三方 | 标准库优先；新增写进 dependencies.md | 评审 + 依赖登记 |
| 顺手改动 | 修 A 时顺手重构 B | 一次提交一件事 | 自查 diff |
| 静默重试 | 失败了偷偷重试掩盖 | 报告失败与原因 | 评审 |

## 一个判断标准

如果你在解释"为什么这次可以破例"，那大概率就是该停下来补规则的时候。
