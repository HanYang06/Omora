# 已知反模式

> 每条都对应一种真实的翻车方式。看到症状，按"正确做法"处理。

| 反模式 | 症状 | 正确做法 |
|---|---|---|
| 假装完成 | "应该可以""理论上没问题" | 附命令与输出；跑不了就说没验证 |
| 改测试迁就实现 | 测试红了就去改断言 | 先证明测试本身错，再改，并写明理由 |
| 内核长业务 | 内核里出现 Idea / Project / 需求 | 挪到插件 |
| 内核碰 UI | 内核校验节点树、认组件名 | UI 数据对内核不透明，只转 |
| 插件 import 内核 | 插件直接 import 内核内部模块 | 只依赖插件 API；缺能力补 API |
| 插件互相 import | A 插件 import B 插件 | 只靠服务名 |
| 提前抽象 | 还没第二个用例就造清单 / 能力 / 依赖图 | 先最小实现 |
| 渲染引擎做领域判断 | 组件里算状态流转、权限 | 判断回 Python 侧 |
| 顺手改动 | 修 A 时重构 B | 一次一件事 |
| 静默重试 | 失败了偷偷重试 | 报失败与原因 |
| 上帝文件 | 一个文件几百行 | 拆职责 |
| 解释破例 | "这次可以例外" | 停下来补规则 |

## 一个判断标准

如果你在解释"为什么这次可以破例"，那大概率就是该停下来补规则的时候。
